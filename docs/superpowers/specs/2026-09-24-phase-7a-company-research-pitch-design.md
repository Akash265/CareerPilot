# Phase 7a — Company Research & Hiring Manager Pitch: Design

Date: 2026-09-24
Status: design approved by user in brainstorming; not yet implemented.
Spec reference: project specification §10 (Application Generation — "Three-bullet Hiring Manager Pitch", "Company research summary"), §12 (Hiring Manager Pitch — Replace Generic Cover Letter as Primary Output), §19 (`application_pitches` — "three-bullet pitch versions and source evidence"), roadmap Phase 7 (Application Package)
Related decisions: D2 (RLS), D6 (never invent/estimate), D7/D8 (model selected by role/tier via env var; deterministic before AI), D20 (per-request random delimiter around untrusted text), D44 (`hasUnsafeText`: one NUL / lone-surrogate choke point before jsonb), D57 (catch `Anthropic.APIError` distinctly from validation errors), D58–D68 (Phase 6: `job_requirements`, evidence catalog, deterministic guard, per-(user, job) advisory-locked versioning). New decisions are numbered from **D69**.

## 1. Scope

The roadmap's Phase 7 bundles five features (pitch, company research, interview preparation, optional cover letter, document storage). It is split; **this document covers Phase 7a only.**

**In scope (7a)**
- **Company research**, per company (`jobs.companyKey`), generated lazily on the first pitch request for that company and reused by every pitch for any of that company's jobs. Facts come from two sources:
  - *web* — Anthropic's server-side web search tool; only text blocks that carry API-provided citations become facts, each stored with its URL, page title and cited text;
  - *internal* — deterministic summary of what the system already holds for that `companyKey` (open roles, locations, posting count). No LLM.
- Manual **Refresh** of a company's research. No TTL auto-refresh.
- **Three-bullet Hiring Manager Pitch** per job — *why this company*, *why this role*, *why this candidate* — generated by one fast-tier structured-output call and checked by a deterministic guard that every bullet cites real evidence of the right kind.
- **Versioned pitches** (`application_pitches.version` per (user, job)): manual Regenerate creates a new version; a **user edit** also creates a new version (`origin = user_edited`).
- API routes + a `PitchPanel` on the existing `/matches/[jobId]` page.
- Upgrade of `@anthropic-ai/sdk` (currently `^0.32.1`, which has no web-search types) across all packages that depend on it, with regression verification of every existing AI path.
- New model tier `ANTHROPIC_MODEL_RESEARCH` (the current web search tool version is not supported on the fast-tier Haiku model).

**Out of scope (deliberate)**
- **Phase 7b:** PDF/DOCX export of the optimized resume and pitch, document storage in MinIO.
- **Later (7c or optional):** interview preparation; optional legacy cover letter.
- A `companies` table / company entity resolution — `companyKey` is the identity. Two different companies that normalize to the same `companyKey` share research (accepted, documented limitation; same key Phase 4 already dedups on).
- Research version history — refresh replaces facts; pitches snapshot the evidence they used (§3), so no audit trail is lost.
- TTL-based or scheduled research refresh; a background worker/queue.
- Any automatic retry loop to improve a pitch; regeneration is user-triggered only (same as Phase 6 decision 3).
- Wiring pitches into application tracking (Phase 9 associates "the version actually sent").

## 2. Decisions taken in brainstorming

| # | Decision | Alternative rejected |
|---|---|---|
| 1 | Split Phase 7; 7a = company research + pitch | All five Phase 7 features in one spec (~30+ tasks); export first |
| 2 | Research facts from Anthropic web search (API citations) **plus** deterministic internal facts | Internal data + user-pasted notes only; our own website fetcher (SSRF/HTML/robots burden) |
| 3 | Research cached one-per-company, manual refresh, age shown in UI | 30-day TTL auto-refresh; fresh research per job |
| 4 | User may edit a pitch; the edit is saved as a new `user_edited` version | Read-only pitch, regenerate only |
| 5 | Two separate calls: a research call that receives **no candidate data**, then a guarded pitch call | One web-search call producing the pitch directly (candidate data and untrusted web text in one context; profile details could leak into search queries; bullet→URL link would be model self-report) |
| 6 | Synchronous in Next.js API routes, no new service | BullMQ worker + status polling |

Each becomes a DECISIONS.md entry (D69 onward) when implemented, plus any made during implementation.

## 3. Data model

All three tables are RLS-scoped (`user_id` defaulting to `current_setting('app.current_user_id')::uuid`, same as every existing table) and get an RLS isolation test (§8).

### `company_research`

One row per (user, company). Unique index on `(user_id, company_key)`.

```
id               uuid pk
userId           uuid
companyKey       text           -- jobs.companyKey
companyName      text           -- display name, from the job that triggered research
status           enum: ok | no_results | failed
                 -- ok: >=1 web fact; no_results: search ran, nothing cited; failed: API error/refusal
errorCode        text, nullable -- short machine code only (e.g. "api_error", "refusal",
                                --  "max_uses_exceeded"); never raw response text
researchModel    text, nullable -- null when status = failed before any call returned
searchCount      integer        -- server_tool_use web_search blocks observed (cost visibility)
researchedAt     timestamptz
createdAt        timestamptz
updatedAt        timestamptz
```

### `company_research_facts`

```
id               uuid pk
userId           uuid
researchId       uuid, FK company_research(id) cascade
sourceKind       enum: web | internal
factText         text           -- the cited text block (web) or generated sentence (internal)
sourceUrl        text, nullable -- web only; http/https only (validated before insert)
sourceTitle      text, nullable -- web only
citedText        text, nullable -- web only; the API citation's cited_text
displayOrder     integer
createdAt        timestamptz
```

**Refresh semantics:** if a refresh's research call ends `failed` (API error / refusal) while a non-`failed` row already exists, nothing is written and the refresh route answers 502 "Research refresh failed; your existing research was kept" — a transient error must never replace good research with nothing. Otherwise a refresh upserts the `company_research` row and deletes + re-inserts all of its facts in **one short transaction** (the network call happens before the transaction opens — §4). Fact IDs therefore change on refresh; pitches are unaffected because they snapshot evidence.

### `application_pitches`

One row per generated or edited version; never updated in place. Unique index on `(user_id, job_id, version)`.

```
id                    uuid pk
userId                uuid
jobId                 uuid, FK jobs(id) cascade
version               integer         -- 1, 2, 3... per (userId, jobId), allocated under an advisory lock
origin                enum: generated | user_edited
parentPitchId         uuid, nullable, FK application_pitches(id) set null  -- the version an edit was based on
companyResearchId     uuid, nullable, FK company_research(id) set null
researchStatusSnapshot enum (same as company_research.status) -- status at generation time
researchedAtSnapshot  timestamptz, nullable
bullets               jsonb           -- exactly 3, ordered company, role, candidate:
                                      -- [{ kind: "company"|"role"|"candidate",
                                      --    text,
                                      --    supported: true | false | null,   -- null = user_edited
                                      --    unsupportedReason: string | null, -- guard's reason when false
                                      --    evidence: [{ id, kind: "research"|"requirement"|"profile",
                                      --                 text, sourceUrl?: string }] }]
requiresReview        boolean         -- true iff any bullet has supported = false, OR the model's own
                                      -- self-report flagged review (can only add caution, D68 precedent)
sourceProfileContentHash text, nullable -- buildResumeSnapshot().contentHash; null for user_edited
generationModel       text, nullable  -- null for user_edited
createdAt             timestamptz
```

A `user_edited` version copies `companyResearchId`, `researchStatusSnapshot`, `researchedAtSnapshot` and each bullet's `evidence` from its parent, sets every `supported`/`unsupportedReason` to `null`, and has `requiresReview = false` (the user is the authority on their own wording).

`evidence[].text` is a **snapshot** copy, so an old pitch remains auditable after a research refresh deletes the fact rows it cited, or after the profile changes.

## 4. Pipeline

New package `packages/application-package` (pure logic + DB, no BullMQ; mirrors `packages/resume-optimization`: `src/{research,pitch,pipeline,testing}`, `eval/`, depends on `@ai-career/ai`, `@ai-career/config`, `@ai-career/db`, `@ai-career/resume-optimization`, `@anthropic-ai/sdk`, `drizzle-orm`, `zod`). `hasUnsafeText` is imported via a new `@ai-career/ingestion/text` subpath export (`./src/normalize/text.ts`, which has no imports) added this phase — not the package root, whose index re-exports `./queue` and would transitively load BullMQ into this worker-free package.

```
POST /api/application-pitches/[jobId]/run
  └─ runPitchGeneration(db, { userId, jobId, anthropicClient, env })
       1. gates (same as Phase 6): job_matches row exists (else no_match → 404),
          eligible (else not_eligible → 400); then buildResumeSnapshot — empty catalog → no_profile → 409.
          The profile check runs BEFORE research so a user without a profile never triggers a paid search.
       2. research = ensureCompanyResearch(db, job, …)
            cache hit (row exists for companyKey AND status ≠ failed) → return it with facts
            (a `failed` row is not reused: the next pitch request retries research automatically;
             `no_results` IS reused — it is a genuine answer, not an error)
            miss → runCompanyResearch()      ── network, OUTSIDE any transaction
                   extractCitedFacts()        ── pure
                   deriveInternalFacts()      ── pure, from that companyKey's open jobs
                   write row + facts          ── one short transaction, ON CONFLICT (user_id, company_key) DO UPDATE
       3. requirements = ensureJobRequirements(...)       ── reused from Phase 6
       4. draft  = generatePitch(anthropicClient, env, { job, research facts, requirements, catalog })
          result = applyPitchGuard(evidence index, draft)  ── pure
       5. insert application_pitches version under
          pg_advisory_xact_lock(hashtext('application_pitches'), hashtext(userId || ':' || jobId))
```

### 4.1 `runCompanyResearch` (research tier)

- **Input:** company name, and — as disambiguation hints only — the job title and the posting URL (`job_postings.url`) of the triggering job. **No candidate/profile/goal data**, so nothing about the user can appear in a search query sent to the web.
- **Request:** `ANTHROPIC_MODEL_RESEARCH` (default in `.env.example`: `claude-sonnet-5`), tool `{ type: "web_search_20260209", name: "web_search", max_uses: COMPANY_RESEARCH_MAX_SEARCHES }` (default 5). System prompt asks for short, standalone factual statements about the company (what it does, products, mission/stated values, stage/size, notable recent news) and to state nothing it cannot cite. Company name and URL wrapped in a D20 random delimiter.
- **Response handling:**
  - `stop_reason: "pause_turn"` → continue by re-sending the conversation (no extra user message), at most 2 continuations; still paused after that → use what was collected.
  - `stop_reason: "refusal"` → `failed` / `refusal`.
  - A `web_search_tool_result` whose `content` is an error object (not a list) → recorded; if no citations were produced at all, `failed` with that error code.
  - `Anthropic.APIError` → `failed` / `api_error`. Research failure is **stored and degrades the pitch; it never fails the pitch** (§5).
- The exact SDK version and web-search tool/result type names are confirmed against the upgraded SDK during planning; the tool version above requires a model from the Sonnet 4.6 / Opus 4.6 generation or later.

### 4.2 `extractCitedFacts` (pure)

Walks the response content. For each `text` block **with a non-empty `citations` array**: one fact with `factText` = block text (trimmed, capped), and source fields from the first `web_search_result_location` citation. Blocks without citations are **discarded** — this, not the prompt, is what guarantees every web fact has a source. Also discards: facts whose URL scheme is not `http`/`https`; any fact for which `hasUnsafeText` is true (NUL / lone surrogate — D44); exact-duplicate fact text. Caps: at most 15 web facts, 500 chars each, cut on a surrogate-safe boundary.

### 4.3 `deriveInternalFacts` (pure)

From the user's open `jobs` rows with this `companyKey`: e.g. "Acme is currently hiring for 4 roles in the system's job data, including Data Engineer and Analytics Engineer (Berlin, Remote)." Always yields ≥ 1 fact because the triggering job itself exists. Deterministic ordering (by title, then id).

### 4.4 `generatePitch` (fast tier)

- `ANTHROPIC_MODEL_FAST`, tool-use structured output validated with Zod — same mechanism as `optimizeResume`.
- Evidence is presented with prefixed IDs: research facts `r:<uuid>`, job requirements `q:<uuid>`, profile catalog entries `p:<sourceFactId>`. All untrusted text (research facts, job-derived requirement text, profile text) is inside a D20 random delimiter and the prompt states it is data, not instructions.
- Output: `{ bullets: [{ kind, text, evidenceIds: string[] }] (exactly 3, one per kind), requiresReview: boolean }`. Bullet text capped at 600 chars by the schema.
- Malformed output → `PitchGenerationValidationError`.

### 4.5 `applyPitchGuard` (pure) — the grounding backstop

For each bullet, `supported = false` (with a reason recorded in the bullet) if any of:
- an evidence ID does not exist in the evidence index for this call;
- an evidence ID is repeated within the bullet (Phase 6 final-review finding: `applyDeterministicGuard` accepted a repeated `sourceFactId`);
- the bullet cites **no** ID of its required kind: company → ≥1 `r:`; role → ≥1 `q:`; candidate → ≥1 `p:`.

Unsupported bullets are **kept and flagged**, never dropped, so a pitch always has three bullets and the UI can show what failed. `requiresReview = anySupportedFalse || draft.requiresReview`. The guard resolves each cited ID to its snapshot `{ id, kind, text, sourceUrl }` for storage.

## 5. Error handling

| Condition | Result |
|---|---|
| No `job_matches` row | `no_match` → 404 "Run Find Matches for this job first" |
| Match not eligible | `not_eligible` → 400 |
| Empty evidence catalog (no confirmed profile) | `no_profile` → 409 "Confirm your profile first" |
| Research call fails / refuses / finds nothing | stored as `failed` / `no_results`; pitch proceeds on internal facts; UI shows "based on posting data only" |
| `Anthropic.APIError` or validation error in `ensureJobRequirements` / `generatePitch` | `unknown` → 502 "Pitch generation failed. Try again." (D57) |
| Refresh whose research call fails while good research exists | nothing written → 502 "Research refresh failed; your existing research was kept" |
| Refresh for a job id that does not exist | 404 |
| Anything else | rethrown (500) — a bug, not an expected failure |
| Invalid `jobId` (not a UUID) | 404 |
| Edit body invalid (not 3 bullets in order, empty, > 600 chars, `hasUnsafeText`, bad JSON, unknown `baseVersionId`) | 400 |

Concurrent first-time research for the same company: both requests may run a (paid) search; the unique index + `ON CONFLICT DO UPDATE` makes the last writer win atomically. Accepted rather than holding a lock across a 30–90s network call; documented as a decision.

**Privacy / logging:** no pitch, profile, requirement or research text is logged; research `errorCode` is a short code, never response text.

## 6. API

| Route | Behavior |
|---|---|
| `GET /api/application-pitches/[jobId]` | `{ versions: PitchView[] (newest first), research: ResearchView \| null }` — research looked up by the job's `companyKey` |
| `POST /api/application-pitches/[jobId]/run` | generate a new version (lazily researching first) → 201 `{ pitch, research }` |
| `POST /api/application-pitches/[jobId]/edit` | body `{ baseVersionId, bullets: [string, string, string] }` (company, role, candidate) → new `user_edited` version copying the base's evidence with `supported: null` → 201 |
| `POST /api/application-pitches/[jobId]/research/refresh` | re-run research for this job's company → 200 `{ research }`; existing pitches unchanged |

Serialization in `apps/web/src/lib/applicationPitch/serializePitch.ts` (mirrors `serializeOptimization.ts`). Source URLs are re-validated as `http(s)` at serialization time (defense in depth).

## 7. UI

`PitchPanel` on `/matches/[jobId]`, below `ResumeOptimizationPanel`:
- Generate (first time) / Regenerate; version selector ("v3 · edited" / "v2 · generated").
- Three labelled bullets (Why this company / role / me). Each has an expandable evidence list: research facts show title + link, requirements show the term, profile facts show the source text.
- Review banner when `requiresReview`, naming the unsupported bullet(s) and why.
- Edited versions: bullets labelled "your wording"; no supported/unsupported badge.
- Edit mode: three textareas pre-filled from the selected version; Save creates a new version.
- Copy button (plain text, three bullets).
- Research line: "Company researched N days ago · Refresh"; if `failed`/`no_results`: "Web research unavailable — company bullet is based on posting data only".
- External links: rendered only for `http(s)` URLs, `target="_blank" rel="noopener noreferrer nofollow"`.
- Loading state that says research may take up to a minute on first generation for a company.

## 8. Testing

**Unit (pure):** `extractCitedFacts` against recorded response-shape fixtures (cited + uncited blocks, multiple citations, web-search error object, `pause_turn` shapes, NUL / lone-surrogate text, `javascript:`/`data:` URLs, duplicates, caps at surrogate boundary); `deriveInternalFacts`; `applyPitchGuard` (one test per rule + all-good); pitch Zod schema; edit-body validation.

**Routes:** each status code in §5/§6. **Components:** `PitchPanel` states (empty, generated, requires-review, edited, research failed, edit save, non-http URL not linked).

## 9. Risks

- **SDK upgrade blast radius:** jumping from 0.32 to a current major may change types/behavior in the three existing AI packages. Mitigation: the upgrade is its own first task, verified by the full suite + real evals before any Phase 7a code lands.
- **Research quality is unmeasured and model-dependent:** web results may favor aggregators over the company's own site. Mitigation: `research-smoke` eval reports it; `allowed_domains`/`blocked_domains` are a later tuning knob, not built now.
- **Cost:** each first-time research costs up to `COMPANY_RESEARCH_MAX_SEARCHES` searches plus research-tier tokens. Mitigation: per-company caching, manual refresh only, `searchCount` stored.
- **Latency:** first pitch for a company may take up to ~90s in a synchronous request. Accepted for a single-user local app (decision 6); revisit with a worker if it proves painful.
- **companyKey collisions** share research across distinct companies — accepted limitation (§1).

## 10. Post-implementation notes

- **§4.1's tool is `web_search_20250305`, not `web_search_20260209`.** The newer tool's server-side "dynamic filtering" (code execution over raw search results) produced text with zero `web_search_result_location` citations, so `extractCitedFacts` (correctly) discarded everything and every research call came back `no_results`. Replaced per D79; see D79 for the measured before/after.
- **§4.3's "in the system's job data" wording deliberately includes the triggering job even if it is closed.** `deriveInternalFacts`'s caller (`ensureCompanyResearch`) selects this company's `open` jobs **or** the triggering job by id, specifically so a real call never yields zero internal facts even when the job the pitch is for has since closed.
- **§4.1/§5's "failed never overwrites good research" is enforced atomically at write time (D74), not from the pre-call read.** `ensureCompanyResearch`'s upsert carries `setWhere: status = 'failed'` on a failed write, so it only overwrites a row whose *currently stored* status is still `failed`; if a concurrent caller already committed non-failed research, the guarded update is skipped and the code re-reads what is actually stored instead of blindly writing over it.
- **A response truncated by `stop_reason: "max_tokens"` with nothing cited is stored as `failed` (`errorCode: "max_tokens"`), not `no_results`.** `no_results` is treated by `ensureCompanyResearch` as a genuine, permanently-cached answer; a truncated response is an incomplete one and must be retried on the next request, which only happens for `failed`.
